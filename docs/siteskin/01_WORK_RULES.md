# SiteSkin 공통 작업 규약

문서 버전: **v0.1** · 작성일: **2026-09-09**  
연결: [안내](00_INDEX.md) · [참고 분석](02_REFERENCE_AUDIT.md) · [테마 양식](03_THEME_TEMPLATE.md)

**상태: 이 문서의 작업 규약과 양식은 모두 제안이다.** 기존 사이트의 실제 구현이나 사용 도구의 지원을 보장하지 않는다. 이번 요청에서 정한 보존·범위 제한을 향후 작업 절차로 구체화한다.

## 1. 변경 계약

| 구분 | 원칙 |
|---|---|
| 디자인 변경 가능 범위 | 허용된 배경·히어로·장식 이미지, 색상·재질·선·그림자·글꼴·여백, 헤더·푸터·메뉴·버튼·카드·입력창·내부 박스의 스타일. 모두 대상 목록과 연결한다. |
| 기능·콘텐츠 보존 | 라우트, 콘텐츠의 의미와 계층, 데이터 바인딩, 인증·권한, API 계약, 검증 로직, 입력·오류 처리, 게임 규칙·확률·배당·금액 계산·거래 흐름, 기존 접근성 및 지원 화면 동작. |
| 조건부 변경 | 레이아웃·크기·문구·상태 표시를 변경해야 하는 경우 영향과 필요성을 밝힌다. 테마 요청만으로 콘텐츠·기능 변경을 정당화하지 않는다. |
| 기본 제외 | 프레임워크 교체, 상태 관리 이관, 대규모 구조 변경, 무관한 리팩터링·정리, 임의의 애니메이션·소리 추가, 의존성·설정 시스템 추가. |
| 외부 요소 | 제공사 로고·브랜드 식별 요소·실제 게임 표지·법적 고지·사용자 콘텐츠는 기본 보존. 권리와 교체 권한이 확인된 범위에서만 조건부 변경한다. |

원본에 맞는 최소 변경을 우선한다. 시각적 불일치의 원인이 특정 리소스 크롭인데 전역 CSS를 바꾸거나, 공통 컴포넌트 문제를 여러 페이지에 복제해서 가리지 않는다.

## 2. 기준 상태와 수동 수정 보존

1. 실제 작업 루트와 적용 지침을 확인한다. 제공 소스와 실행 페이지의 관계를 버전·빌드·명시적 제공 정보로 확인한다. URL·외형만으로 같은 소스라고 판단하지 않는다.
2. 기존 파일·사용자 변경·실행 중 서비스·의존성·문서 체계를 읽기 전용으로 조사한다. Git 저장소가 있을 때만 기존 상태를 확인한다. 요청 없이 저장소·브랜치·커밋·태그를 만들지 않는다.
3. 실행 ID와 기준 버전을 부여한다. Git 기준이 없다면 제공 압축 파일/폴더 식별자, 시점, 관련 파일 경로·크기·SHA-256을 기준으로 사용한다. 해시는 내용 비교 근거이지 사용 권한의 증거가 아니다.
4. 변경 예정 파일·이미지의 원본을 덮어쓰지 않는 별도 백업에 보관하고 복원 경로를 기록한다. 민감한 설정·키를 보고서나 외부 서비스에 복사하지 않는다.
5. 주요 화면·뷰포트·상태·기능 결과를 기준 자료로 저장한다. 이미 있던 오류나 잘림을 따로 표시하여 이번 변경의 회귀와 구분한다.
6. 직전 자동화 결과와 현재 파일의 해시가 다르면 수동 수정 가능성으로 표시하고 자동 교체를 보류한다. 신규 수동 수정 파일도 보존 목록에 등록한다. 차이를 검토한 뒤 병합·분리·유지 중 필요한 범위를 결정한다.

백업 범위와 경로는 실제 프로젝트에 맞춰 최소한으로 정한다. 원본 전체를 다른 프로젝트로 이동하지 않는다. 복구 과정에서도 실행 후 발생한 사용자 변경을 덮어쓰지 않는다.

## 3. 원샷 실행의 정의와 완료 기준

원샷 실행은 사용자가 테마와 필요한 입력을 지정하여 **한 번 요청하면 Codex가 아래 단계를 내부적으로 수행하는 작업 방식**이다. 단일 프롬프트나 단일 이미지 호출로 모든 결과를 보장한다는 뜻이 아니다. 진행 기록을 남겨 실패한 의존 단계부터 재개한다.

| 단계 | 입력·수행 내용 | 기록할 결과 | 단계 완료 기준 |
|---|---|---|---|
| S1 대상·기준 확인 | 원본 인수, 범위·기준 버전·권한·보존 상태 확인 | 대상/버전/기준 화면/파일 목록/기능 기준 | 실제 대상과 소스 관계 확인, 원본과 수동 수정 보호 가능 |
| S2 누락 검사 | 테마 DNA, 리소스·UI 목록, 상태·뷰포트, 도구 사양 검사 | 입력 누락과 의존 단계, 생성 가능 여부 | 다음 단계에 필요한 정보가 채워지거나 해당 대상만 보류됨 |
| S3 변경 계획 | 이미지/CSS/컴포넌트 분류, ID→파일→사용 위치 연결, 영향 범위·복구 계획 | 변경 파일, 공유 영향, 고정 제외 목록 | 허용 범위 안에서 최소 변경이 설명되고 모든 대상이 추적됨 |
| S4 대표 영역 검증 | 실제 목록 중 대표 히어로, 반복 카드, 기능 밀집 패널, 공통 헤더 등으로 규칙 시험 | 화면 비교, 크롭·상태·가독성 충돌, 규칙 수정 | 대표성 있는 충돌을 해결하거나 관련 확장을 보류함. 별도 미감 승인은 승인 상태로만 기록 |
| S5 전체 반영 | 필요한 리소스만 생성·선별·검증하고 전체 대상 UI에 적용 | 독립 파일, 결과 버전, 실제 적용 파일, 누락·실패 목록 | 적용 대상마다 성공/실패/보류/고정 보존 중 하나가 기록됨 |
| S6 검증 | 원본 대비 화면·기능·반응형·상태·보존 비교 | 자동·수동 검사와 결과, 남은 차이 | 합의한 필수 검사 완료. 실패를 성공으로 취급하지 않음 |
| S7 보고 | 변경·미완료·복구·승인 대기·다음 조치 정리 | 실행 결과 요약과 재개 지점 | 누락을 숨기지 않고 실제 적용 상태와 승인 상태를 별도 보고 |

중간 확인은 정확성이나 권한 때문에 필요한 경우에만 요청한다. 이미 허용된 가역적 작업은 계속한다. 필요한 질문이 생기면 의존하지 않는 조사·문서 작업은 진행한다. 배포·외부 발행은 범위와 권한에 명시된 경우에만 별도 완료 처리한다.

## 4. 이미지와 UI의 책임 분리

| 대상 | 처리 기준 | 생성 전에 확인할 것 |
|---|---|---|
| 장면·배경·히어로·일러스트·장식 | 분위기와 구도가 핵심이고 교체 권한이 있으면 이미지 생성 후보 | 실제 표시 창, 크롭·초점·안전 영역, 참조 역할 |
| 버튼·입력창·패널·표·경기 데이터·상태 | 기존 HTML/CSS/벡터/컴포넌트를 유지하고 스타일을 최소 변경 | 의미·상태·키보드·터치·콘텐츠 증가 대응 |
| 기존 SVG·아이콘 | 원형 보존. 허용된 색/컨테이너 조정부터 검토 | 원본 형태와 의미, 브랜드 여부, 수정 권한 |
| 제공사 로고·실제 표지 | 기본 보존. 식별·계약·콘텐츠 정확성이 우선 | 권리자, 공식 변형, 최소 여백, 배경 대비 |
| 텍스트가 합쳐진 이미지 | 분리 여부와 수정 권한부터 조사 | 같은 문구가 HTML에 있는지, 다국어·긴 문구 필요 여부 |

HTML 제목·설명·숫자·버튼이 이미지 위에 있으면 생성 이미지에 해당 문구·버튼·가짜 UI를 다시 넣지 않는다. 프롬프트에 텍스트 소유자(HTML/이미지), 비워 둘 위치, 시각적 초점을 명시한다. 모든 글자를 무조건 금지하지 않고, 승인된 이미지 내 문자나 원본 콘텐츠의 표식은 별도 정책으로 관리한다.

사이트 전체를 하나의 합성 이미지로 대체하지 않는다. 구조적 UI의 테마 일관성은 동일한 그림을 붙이는 방식이 아니라 색·선·간격·타입·상태 규칙을 공유하는 방식으로 만든다.

## 5. ID와 기록 연결

### 5.1 ID 규칙

- 영역: `REF-A001`, UI 후보: `REF-U001`, 이미지 역할: `REF-R001`처럼 별도 종류를 사용한다. `REF-`는 이번 참고 대상 전용이다.
- 실제 원본 인수 시 `SRC-A###`, `SRC-U###`, `SRC-R###`를 별도 발급한다. 여기 적은 `SRC-` 형식은 제안이며 현재 생성된 실제 대상 ID가 아니다.
- ID는 최초 발급 뒤 순서 변경·파일 교체·테마 변경으로 바꾸지 않는다. 없어진 ID는 폐기 표시하고 재사용하지 않는다.
- 역할 ID와 실제 소스 경로·DOM 관찰 선택자·리소스 URL을 별도 필드에 둔다. 배포된 해시 클래스명을 원본 컴포넌트명으로 취급하지 않는다.
- 하나의 파일이 여러 위치에서 쓰이면 공유 관계와 각 위치의 크롭을 함께 기록한다. 같은 역할이 독립 변경되어야 하면 새 ID와 파생 관계를 부여한다.

### 5.2 최소 기록 양식

처음에는 기존 문서의 표로 관리할 수 있다. 이 양식 때문에 별도의 데이터베이스나 설정 시스템을 도입하지 않는다. `확인 필요` 값을 실제 값으로 채우기 전에는 생성·적용 입력으로 사용하지 않는다.

| 기록 묶음 | 필수 필드 |
|---|---|
| 대상과 근거 | 대상 ID·이름·유형, 영역 ID, 페이지/라우트, 관찰 URL, 기준 버전, 확인 시점·뷰포트·상태, 근거 파일, 사실 상태 |
| 소스·참조 관계 | 실제 소스 경로, 현재 리소스 URL, 참조하는 파일/컴포넌트/스타일, 사용 위치별 표시 방식, 공유 대상 ID, 소유·교체 권한 |
| 제작 규격 | 원본 W×H, 표시 W×H와 비율, fit/position/반복, 안전 영역, 알파/파일 형식, 반응형 변형, DNA 규칙 ID, 참조 이미지와 역할, 텍스트 소유자 |
| 생성 이력 | 실행 ID·대상 ID·시도 ID, 테마 버전, 정확한 프롬프트, 참조 파일/버전/해시, 실제 도구·모델·설정, 요청 수·실제 출력 수, 지원 확인 결과 |
| 결과와 적용 | 결과 버전, 생성 파일, SHA-256, 원본과의 계보, 기술 검증 결과, 디자인 승인 여부·주체·시점, 실제 적용 파일과 적용 시점 |
| 보존 | 고정 여부·이유·기준 해시, 수동 수정 여부·내용·주체·시점, 허용된 교체 범위 |
| 수정·실패 | 수정 이유, 영향 범위, 실패 유형, 재시도 횟수, 재개 지점, 검증 결과, 복구 파일·결과 |

연결 방향: **테마 DNA 규칙 → 대상별 제작·UI 명세 → 프롬프트 또는 스타일 변경 → 결과 파일·코드 위치 → 사용 페이지와 상태 → 검사 근거 → 승인·고정 기록**. 역방향으로도 실제 적용 파일에서 대상 ID와 테마 버전을 찾을 수 있어야 한다.

### 5.3 단위·안전 영역

원본 픽셀 크기, 브라우저 CSS px, 스크린샷 픽셀, 생성 출력 규격을 각각 구분한다. DPR과 뷰포트를 기록한다. 비율은 `W ÷ H`로 계산한다. 이미지 박스와 `contain` 안에 실제 그려지는 내용 크기도 구분한다.

안전 영역 좌표는 기본적으로 **표시 이미지 박스의 좌상단을 (0,0), 우하단을 (1,1)**로 정규화해 기록하고, 필요하면 해당 뷰포트의 CSS px를 병기한다. 원본 이미지 좌표를 사용하면 원점을 명시한다. `cover`로 잘리는 영역은 표시 창 기준으로 검증한다. 긴 문구·다국어·다른 뷰포트에 대한 여유를 원본 조사 후 결정한다.

생성 비율은 원본 파일의 비율을 무조건 복제하지 않고 실제 표시와 크롭 전략으로 정한다. 사용자가 비율만 지정하면 비율만 필수 검사한다. 정확한 픽셀 크기가 지정되었을 때만 그 크기를 필수 조건으로 삼는다. 도구가 지원하지 않는 크기를 약속하거나 임의 크롭·리사이즈·형식 변환으로 충족했다고 처리하지 않는다.

## 6. 생성 도구와 독립 파일 규약

실행 시점에 도구 사용 가능 여부, 사용자 권한·비용 범위, 참조 이미지 입력 방식·개수, 실제 출력 개수, 해상도·비율·투명도·형식 지원을 확인하고 기록한다. **이번 단계에서는 어느 생성 도구도 검증하지 않았다.** 특정 플러그인·유료 API·외부 생성 서비스를 기본 의존성으로 지정하지 않는다.

리소스별로 독립된 결과 파일을 저장한다. 요청 5개와 출력 5개는 별개이며 실제 파일 수와 읽기 가능한 이미지 메타데이터를 검사한다. 콜라주·합본 하나를 여러 ID의 완료 결과로 등록하지 않는다. 사용자가 합본을 요청한 경우에만 별도 합본 대상 ID로 취급한다.

원본·후보·승인본·적용본의 경로와 상태를 구분한다. 경로는 프로젝트와 사용자 저장 위치 지시에 맞춰 확정하며 충돌 시 새 버전을 사용한다. 승인본·원본을 덮어쓰지 않는다. 생성된 파일은 읽기·개수·규격·내용 검증을 통과해도 자동 승인되지 않는다.

## 7. 승인 결과 고정과 재실행

| 상황 | 처리 |
|---|---|
| 승인 + 고정 | 전체 재실행에서 자동 교체·재생성하지 않는다. 사용 위치와 해시를 검사하고 보존 결과로 보고한다. |
| 승인 + 미고정 | 승인본을 보관한다. 현재 요청에 해당 대상의 교체가 포함된 경우에만 새 후보 버전을 만든다. |
| 미승인 후보 | 재시도 대상이 될 수 있지만 실패 이유와 계보를 남긴다. 승인본 경로로 승격하지 않는다. |
| 수동 수정 있음 | 자동 생성 기준과 현재 내용의 차이를 보호한다. 대상 범위 확인 없이 덮어쓰지 않는다. |
| 새 테마와 고정 결과가 충돌 | 고정 결과를 유지하고 충돌을 보고한다. 고정 해제 또는 별도 변형에 필요한 결정만 요청한다. |

고정은 파일만 보호하는 것이 아니다. 공통 CSS 변경으로 고정 이미지의 크롭·크기·프레임·문구 가독성이 바뀌는지도 검사한다. 컴포넌트 고정에는 관련 상태와 사용 위치를 포함한다. 사람의 미감 판단이 필요한 결과는 승인 주체의 판단을 기록하며 테스트 통과를 디자인 승인으로 대체하지 않는다.

## 8. 국소 수정 절차

1. 대상 ID·현재 적용 버전·고정 상태·수동 수정·모든 사용 위치를 확인한다.
2. 수정 원인을 아래 표로 분류한다. 파일을 먼저 고른 뒤 문제를 맞추지 않는다.
3. 공유 컴포넌트·파일을 바꾸면 영향을 받는 페이지와 상태를 기록한다. 특정 위치만 바꾸라는 요청이면 원본 구조 안에서 최소한의 개별 변형을 검토한다.
4. 변경 전 자료를 보관하고 허용 범위의 최소 수정 및 새 결과 버전을 만든다.
5. 수정 위치와 공유 영향 위치를 재검증한다. 기존 기능 및 고정 결과 보존도 검사한다.
6. 수정 이유·검사·승인·적용 파일·보존 여부를 기록한다. 반복 규칙을 바꿨다면 테마/규약 버전과 영향을 연결한다.

| 문제 | 우선 수정 대상 | 확인 범위 |
|---|---|---|
| 전체 스타일 불일치 | 테마 DNA/적용 규칙 | 전체 대표 영역과 고정 충돌 |
| 특정 이미지 구도·비율 | 해당 리소스 명세·후보 | 해당 표시 창과 모든 공유 크롭 |
| 반복 UI 문제 | 공통 스타일/컴포넌트 | 모든 사용 페이지·상태 |
| 한 영역 배치 | 해당 부모 컨테이너·영역 | 인접 요소·반응형·긴 콘텐츠 |
| 기능 장애 | 관련 코드·상태 전환·기능 기준 | 원본과 같은 재현 흐름 및 회귀 |

## 9. 실패·재시도·원상 복구

작업 단위마다 `대기 / 진행 / 성공 / 실패 / 보류 / 건너뜀`을 기록한다. 건너뜀에는 고정 보존·범위 제외 등 이유가 필요하다. 승인·고정 플래그는 이 실행 상태와 별개다.

- 도구 일시 실패: 오류와 시도를 기록하고 해당 단위만 제한적으로 재시도한다. 기본적으로 같은 조건의 자동 재시도는 최초 실패 후 최대 2회까지를 제안하며, 실행 전 비용·시간 조건에 맞춰 정한다. 해결되지 않으면 보류하고 다른 독립 대상을 계속한다.
- 출력 규격 실패: 실제 파일 수·비율·알파·형식과 요구를 비교한다. 원인에 맞춰 해당 리소스 규격/프롬프트/도구 선택을 수정한다.
- 디자인 실패: 해당 후보를 미승인으로 남기고 구도·재질·가독성 등 구체적 차이를 기록한다. 성공한 다른 이미지까지 다시 만들지 않는다.
- 공통 규칙 결함: 여러 대상의 같은 실패가 규칙에서 비롯되었는지 확인한 뒤 해당 규칙과 의존 대상만 갱신한다. 일회성 실패를 무조건 전역 금지 문구로 추가하지 않는다.
- 코드·기능 실패: 가장 작은 원인 범위를 수정한다. 해결할 수 없으면 이번 실행이 바꾼 파일/참조만 기준 상태로 복구하고 복구 후 검사한다.
- 권한·지원·필수 입력 부족: 해당 의존 단계만 보류한다. 지원하지 않는 기능을 우회 설치·계정 변경으로 해결하지 않는다.

재개 시 실행 기록, 마지막 성공 결과·해시, 변경된 입력·테마 버전, 실패한 의존 관계를 비교한다. 이미 성공한 결과가 새 입력에도 유효하면 재사용한다. 실패한 작업이 공유 파일을 바꾸었다면 그 파일에 의존하는 검사만 다시 수행한다.

보고 단위는 리소스/컴포넌트이고 도구 호출 횟수는 별도로 기록한다. 리소스 시도 수 = 성공 + 실패 + 실행 후 보류. 시작하지 않은 보류와 건너뜀은 별도 합계로 기록한다. 승인/반려/승인 대기는 결과 버전별 별도 집계이므로 성공 수에 더하지 않는다.

## 10. 실제 원본 인수와 문서 완성 절차

**확인 필요:** 다음 항목은 실제 원본을 받은 뒤 조사한다. 참고 분석서의 값으로 대체하지 않는다.

| 인수 항목 | 조사 방법 | 문서 반영 위치·완료 증거 |
|---|---|---|
| 소스·버전·대상 관계 | 제공 경로/버전/빌드 정보를 실행 URL과 대조 | INDEX의 인수 정보 + 실제 원본 분석서의 기준 정보 |
| 실행 방법 | README·적용 지침·패키지 스크립트·잠금 파일·환경변수 이름 확인, 기존 방법으로 실행 | 실제 원본 분석서에 정확한 명령·포트·URL·환경. 비밀 값은 제외 |
| 주요 페이지 | 라우트·메뉴·직접 진입·권한별 접근을 대조 | 페이지/상태/뷰포트 목록과 기준 화면, 각 `SRC-A` 연결 |
| 공통 컴포넌트 | 실제 import/사용 위치와 렌더링 계층 추적 | `SRC-U`→실제 경로→모든 사용 페이지 관계 |
| 스타일 구조 | 전역/지역 CSS, 토큰, 테마, 라이브러리·인라인 우선순위 조사 | 수정 가능 위치, 충돌·상속·우선순위, 고정 보호 범위 |
| 이미지 참조 관계 | IMG, CSS 배경, SVG, srcset/picture, API·CMS·동적 경로 및 lazy load 조사 | `SRC-R`→URL/원본 경로→상태별 표시·공유·권리 정책 |
| 반응형 | 선언된 breakpoint와 실제 뷰포트를 함께 검사 | 지원 크기·재배치·숨김·가로 스크롤·터치·DPR 기준 |
| 기능·데이터 | 인증, 입력·오류, API·권한, 계산, 빈/로딩/실패 상태 조사 | 보존 계약, 허용된 테스트 절차와 비교 결과 |
| 기존 검증 | 문서·CI·package scripts 등에서 실제 명령 확인 | 실행 가능한 typecheck/lint/test/build/smoke 명령과 기존 실패 |
| 수동 수정·승인본 | 현재 파일과 기존 적용 기록·해시 비교, 제공자의 보존 목록 확인 | 고정/수동 수정 목록 및 복원 자료 |
| 이미지·폰트 권리 | 제공 정보·브랜드 가이드·라이선스 확인 | 리소스별 교체 허용 여부·참조 사용 범위 |
| 테마·도구 | THEME_TEMPLATE 작성, 도구의 현재 기능·비용·권한 확인 | 테마 버전·제작 명세·지원 확인일·필수 누락 목록 |

원본 분석서는 기존 프로젝트 문서 체계를 우선한다. 없으면 `04_SOURCE_AUDIT.md`를 추가하는 방안을 사용한다(제안, 현재 미생성). INDEX에 실제 경로와 읽는 순서를 등록한다. 예시 분석서는 덮어쓰지 않고 `REF-`와 `SRC-`의 관계를 필요한 경우에만 별도 연결한다.

조사가 끝나면 테마 양식의 리소스·UI 대상에 실제 원본 ID와 경로를 채운다. 예시의 1920px 너비·색·파일 수·데모 응답을 실제 요구사항으로 이식하지 않는다.

배당 상승/하락, 오류/성공, 선택/비활성처럼 의미를 전달하는 색은 테마 장식색과 구분해 매핑한다. 색 외에 기호·문구·테두리·상태 속성 등 기존 단서를 보존한다. 수치·금액의 계산은 디자인 작업에서 바꾸지 않는다.

실제 가입·결제·베팅 등 거래를 디자인 관찰용으로 실행하지 않는다. 필요한 기능 검증은 허용된 데모·테스트 계정·테스트 환경에서 범위를 확인한 뒤 수행한다. 브라우저 응답, 서버 처리, 외부 게임 연결을 각각 구분해 기록한다.

검사 명령은 프로젝트에 있는 방법을 우선하며 문서 작업만을 위해 무거운 테스트 환경을 설치하지 않는다. 자동 검사가 통과해도 시각 확인과 디자인 승인까지 완료했다고 보고하지 않는다.
