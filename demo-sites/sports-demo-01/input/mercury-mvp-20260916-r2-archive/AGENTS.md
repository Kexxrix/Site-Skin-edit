# MERCURY — 작업 공통 규칙

문서 세트: MVP R2 · 2026-09-16  
목적: 하나의 정밀한 스포츠 데모 화면을 같은 기준으로 구현한다.

## 읽기 순서와 문서 책임

1. `AGENTS.md`
2. `STATE.md`
3. `DESIGN_SPEC.md`의 Global·Visual Locks 및 담당 영역
4. 관련 코드

확정 이유나 충돌 판단이 필요할 때만 `DECISIONS.md`의 해당 결정을 읽는다.
현재 지시를 담는 운영 문서는 이 4개뿐이다. HISTORY, HANDOFF, TASKS, NOTES, 별도 감사 MD를 만들지 않는다.
`references/`는 관찰용 자료, `assets/branding/`은 사용자가 적용을 지시한 실제 브랜드 자산이다.
기존 프로젝트의 필수 설정·소스·Sites 메타데이터는 보존한다. 다른 문서를 일괄 삭제하지 않는다.
R2는 R1 및 이전 `SPORTS_DEMO_CYCLE_01.md`의 실행 기준을 갱신한다. 과거의 이미지 전면 금지·가상 경기만 사용·단일 담당 운영 지시를 중복 적용하지 않는다.

## 스레드 역할과 수정 범위

| 역할 | 책임 | 경계 |
| --- | --- | --- |
| GPT Web Work | 목표·계획·피드백·다음 지시 정리, 사용자 제작 자산 전달 | 기록과 실제 구현 완료를 구분 |
| Codex 전체 진행 스레드 | 범위 지정, 충돌 방지, 결과 통합, 진행·판정 관리 | STATE·DESIGN_SPEC·DECISIONS의 관리 책임 |
| Sites 제작 구현 스레드 | 기존 MERCURY 소스 수정, 미리보기, 기능 검증, 배포 | 지정 범위와 승인 자산 보존, 해당 Site의 소스·배포 소유권 유지 |
| 품질 감사 스레드 | 실제 화면·상태·효과의 독립 감사, 개선점 보고 | 코드·디자인 기준을 임의 변경하지 않음. 직접 수정하여 자신의 결과를 스스로 통과시키지 않음 |

- 사용자 설명에 따르면 진행·구현 스레드 2개는 운영 중이다. 감사 스레드 추가 방식은 지시에 반영하되, 실제 생성·실행 여부는 STATE에서 따로 확인한다.
- 이 구성은 별도 작업 스레드 간 역할 분리다. 자동 서브 에이전트 생성이나 다수의 병렬 UI 코딩을 시작하라는 지시가 아니다.
- Sites의 현재 스킬과 소유권 규칙을 따른다. 부모 Site의 체크아웃·배포를 자식 에이전트가 임의로 인수할 수 있다고 가정하지 않는다.
- 작업자는 할당 범위만 수정한다. 공통 스타일이나 다른 영역에 변경이 필요하면 진행 스레드에 영향과 제안을 보고한다.
- 감사 보고는 채팅과 캡처로 전달하고 최신 판정만 STATE에 반영한다. 운영 문서를 늘리지 않는다.

## 수정 전

- 기존 MERCURY의 코드와 실제 화면부터 확인한다. URL, 작업 폴더, project_id, 소스 버전이 같은 대상을 가리키는지 확인한다.
- 대상: `MERCURY`, https://mercury.kexxadrix.chatgpt.site/
- 첫 공개 디자인은 반려됐다. 기존 갈색 테마·카드 구조·장식을 승인된 외형으로 보존하지 않는다.
- 정상 작동하는 배당 선택·해제·교체·슬립 반영·삭제·계산과 단일 페이지 구성은 보존한다.
- TITAN 홍보 사이트와 HADES, 다른 페이지, 실제 인증·입출금·베팅 시스템은 작업 범위 밖이다.
- 실제 경기·팀·리그 자료와 수집 이미지를 읽고 정적 데이터로 적용하는 것은 허용된다. 지속적인 실시간 서버 연동은 필수가 아니다.
- 관련 컴포넌트·스타일·데이터를 먼저 읽는다. 기존 프레임워크·의존성·잠금 파일을 특별한 이유 없이 교체하지 않는다.

## 디자인과 자산

- DESIGN_SPEC가 기준이다. `LOCKED`는 사용자 확정, `PROPOSED`는 실행 가능한 초기안, `UNVERIFIED`는 미확인이다.
- 제안값으로 구현을 진행할 수 있다. 담당자 검수만으로 사용자 승인 상태로 바꾸지 않는다.
- 디자인 해석에 중요한 차이가 있으면 해당 부분의 비교 시각 자료와 구체적인 질문을 제시한다. 사용자에게 모든 요소를 직접 그리라고 요구하지 않는다.
- 기본 UI는 Pretendard JP, 일본어는 Heisei Mincho Std, 필요한 강조 영역은 Omnigothic, 스코어는 DIN Condensed다. 기존 폰트 파일·등록·실제 렌더링을 확인하고 임의 대체하지 않는다.
- 헤더 레터링과 좌측 엠블럼은 제공된 원본 이미지를 사용한다. 텍스트나 임시 벡터로 재제작하지 않는다.
- 스포츠 자산은 `E:\codexwork\Site-Skin-edit\TEMP\Sports-Images`에서 실제 수집 상태와 메타데이터를 먼저 확인한다. 미확인 폴더를 확인했다고 보고하지 않는다.
- 확보된 국기·리그·팀·종목 이미지를 적극 사용하되 실제 데이터와 맞춘다. 이미지에 맞춰 패널을 키우지 않고, 정해진 슬롯에 비율을 유지해 표시한다.
- 사용자 제작이 필요한 아이콘·패널 자산은 위치·표시 크기·필요 상태 등을 적어 요청한다. 사용자가 이 스레드에 전달하면 다음 지시에 실제 파일을 포함한다. 임의 이미지 생성은 하지 않는다.
- 패널·탭·버튼을 기본 스타일이나 임시 박스로 끝내지 않는다. 구조·색 이름의 존재를 시각 완성으로 간주하지 않는다.
- 강한 골드 글로우·광택·대기·호버는 허용된 방향이다. 효과를 일괄 약화하거나 금지하지 않는다. 구체 표현은 사양으로 관리한다.
- 반려된 넓고 흐릿한 대각선 카드 오버레이와 끊긴 두꺼운 모서리 광택선은 재사용하지 않는다.
- 1920 기준 고정 화면이다. 큰 화면에서 중앙 확장, 모바일·태블릿 재배치, 전체 축소 맞춤은 구현하지 않는다.

## Sites 실행·배포

1. 실행 시 제공되는 sites-building 및 필요한 미리보기·hosting 지침을 읽고 기존 프로젝트를 재사용한다.
2. 기존 `.openai/hosting.json`과 Sites 조회 결과로 project_id를 확인한다. URL에서 ID를 추측하거나 대체 사이트를 새로 만들지 않는다.
3. 이 프로젝트의 고정 화면·지정 폰트·제공 자산·시각 감사 조건이 일반적인 자동 제작 기본값보다 우선한다.
4. Sites 도구의 호출 성공이나 배포 성공 자체를 디자인 승인으로 취급하지 않는다.
5. 개선 구현을 요청받았을 때는 검증된 수정본을 기존 MERCURY의 공개 범위를 유지해 배포한다. 이미 허용된 공개 배포를 매번 다시 묻지 않는다.
6. 대표 요소 검수판을 완성된 MVP라고 보고하지 않는다. 중간판 공개를 요청받으면 검수 범위를 명시한다.
7. **문서 기록만 요청된 턴에는 사이트 수정·배포·감사 스레드 실행을 하지 않는다.**

## 검증과 기록

- 기능·시각·효과·사용자 승인을 분리한다. 실제 화면을 보기 전에 작업 완료를 주장하지 않는다.
- 감사자는 https://wog-1000.com/ 을 직접 열어 비교한다. MERCURY 사양 준수와 WOG를 하한점으로 한 완성도를 각각 판정한다. WOG 외형 복제나 문서에 사이트 내용을 재서술하는 작업은 필요하지 않다.
- 목표 폭과 더 넓은 화면의 폭 고정을 실제 확인한다. 효과는 기본/호버/눌림/선택/잠금 상태와 움직임을 확인한다.
- 실제 적용 폰트, 이미지와 경기 정보의 일치, 깨짐·왜곡·레이아웃 변화도 확인한다.
- 변경에 맞춰 기능을 검증하고 기존 필수 빌드 검증을 지킨다. 구현을 그대로 따라 쓰는 불필요한 테스트 파일을 늘리지 않는다.
- 실제 구현과 사양이 다르면 차이를 진행 스레드에 보고한다. 자료 확인 불가·사용자 확인·직접 확인을 구분한다.
- 새 피드백과 다음 지시는 STATE의 현재 문제·대기 지시에 반영하고, 실행 기준은 DESIGN_SPEC, 뒤집으면 안 되는 결정은 DECISIONS에 반영한다. 같은 내용을 세 파일에 길게 반복하지 않는다.
- `접수·기록 / 자산 확보 / 구현 / 직접 검증 / 사용자 승인` 상태를 구분한다. 받은 지시를 이미 구현한 것처럼 적지 않는다.
- STATE는 현재 상태로 교체한다. 이전 진행·결과 중 현재 판단에 필요한 기준만 남기며, 과거 전문과 수정 이력은 기존 대화·버전으로 추적한다.
- 사용자의 정지 지시 중에는 갱신도 멈춘다. 이후 기록 요청을 받으면 미반영 내용을 모아 갱신한다.

```text
변경 영역:
변경 파일:
구현 또는 기록 내용:
검증: 기능 / 시각 / 효과 / 자산 / 사용자 확인을 구분
남은 문제:
DESIGN_SPEC와 다른 부분:
```
