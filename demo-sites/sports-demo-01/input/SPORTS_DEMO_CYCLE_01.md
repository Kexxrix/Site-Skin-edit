# Codex + Sites 작업지시서 — 스포츠 데모 첫 사이클

개정: R2 · 2026-09-16  
문서 상태: 구현 실행용. 기존 지시서와 Sites 검토 부록을 이 문서로 통합·대체한다.  
이번 실행 범위: 이미지 없는 대표 UI 제작 → 수정 통제 테스트 → 사용자 1차 검수 제출.  
후속 범위: 대표 UI 승인 후 전체 단일 페이지 완성.

## 1. 바로 실행할 작업

**Sites 스킬을 사용해 블랙·골드·아이보리 스포츠베팅 데모의 대표 UI를 제작하라.** 아래 고정 조건에 따라 실제 브라우저에서 확인 가능한 결과물을 만들고, 지정한 부분만 수정되는지 검증한 다음 사용자에게 제출한다. 계획 설명이나 문서 작성만으로 종료하지 않는다.

이번 첫 제출은 로컬 제작·시각 검수 단계이며 **배포하지 않는다.** 대표 UI 검수 결과를 반영한 뒤 전체 페이지로 확장한다. 사용자가 후속 요청에서 링크 배포를 지정하면 그 요청에 따라 Sites 호스팅을 진행한다.

- 이 대화에서 작성한 지시서를 전달받는 **구현 담당 Codex가 실제 사이트를 제작**한다.
- 타이탄 홍보 사이트와 HADES는 수정 대상이 아니다. `RickyJayPark/titan_promotion`에 작업하지 않는다.
- 지정된 개별 스포츠 데모 작업 폴더가 있으면 재사용한다. 지정된 소스가 없다면 기존 프로젝트와 분리된 새 스포츠 데모 폴더에서 시작한다. 다른 사이트를 임의로 복제하거나 덮어쓰지 않는다.
- 명칭은 아직 확정되지 않았다. 기존 작업 대상의 브랜드가 있으면 유지한다. 새 작업이면 `COBALT`를 구성 검토용 임시 명칭으로 사용하고 첫 보고에서 임시임을 밝힌다.
- 이 문서는 Figma 원본 제공을 전제로 하지 않는다. 현재의 고정 조건과 참고 화면으로 먼저 제작한다.

## 2. 반드시 유지할 제품 범위

목적은 방문자가 실제 사이트처럼 디자인과 조작감을 체험하고, 그 스타일의 제작 상담을 받을 수 있게 하는 것이다. 실제 경기 데이터·게임 실행·실금전 거래는 연결하지 않는다. 상태와 수치는 가상 데이터로 동작시킨다.

| 영역 | 구성과 조건 |
| --- | --- |
| 화면 전체 | 1920×1080 모니터용 데스크톱 단일 페이지 |
| 헤더 | 브랜드, 주요 카테고리, 계정 동작. 실시간 스포츠가 처음부터 선택된 상태 |
| 왼쪽 | 바로가기 메뉴, 검색, 스포츠별 바로가기, 간단한 홍보 패널 |
| 중앙 | 실시간 스포츠 → 마감임박 → 인기경기. 기본 3열 베팅카드 목록 |
| 오른쪽 | 계정 상태, 충전·환전·베팅내역, 베팅슬립, 문의·공지, 간단한 이벤트 패널 |
| 스크롤 | 헤더 유지. 좌측·중앙·우측 콘텐츠는 각각 독립 스크롤 |
| 중앙에서 제외 | 히어로 배너, 콘텐츠 바로가기 이미지 카드, 카지노·슬롯 갤러리 |
| 기기 대응 | 모바일·태블릿 재배치, 반응형 분기, 전체 화면 축소 맞춤은 구현하지 않음 |
| 매체 | 첫 사이클은 이미지·영상 에셋 없이 제작. HTML/CSS와 기본 벡터 UI 아이콘은 사용 가능 |
| 효과 | 강한 글로우·호버·광택·대기 효과도 시도 가능. 검수로 강도를 조절 |

헤더에 다른 카테고리가 보여도 그 카테고리의 완성된 페이지를 추가하지 않는다. 메뉴의 선택·안내 동작은 현재 단일 페이지 안에서 처리한다. 사이트를 소개하는 별도의 랜딩 페이지도 만들지 않는다.

## 3. Sites 사용 방식과 실행 조건

### 시작할 때

1. 실행 환경에 `sites-building` 스킬과 필요한 Sites 도구가 실제로 제공되는지 확인하고, 설치된 지침을 읽는다. 제공되지 않으면 Sites 실행이 불가능한 범위를 명확하게 보고한다. 일반 코드 작업을 Sites 실행으로 표현하지 않는다.
2. 해당 프로젝트에서 Sites 지침에 따라 실행 환경을 확인하고 설정한다. 기존 소스·기술 스택·의존성이 있으면 보존한다. 빈 작업 폴더라면 Sites의 새 프로젝트 설정 절차를 따른다.
3. 이번 작업은 브라우저 시각 검수가 필수다. 현재 managed-linux 지침을 따르는 환경에서는 시각 검수를 지원하는 capability path를 사용한다. 실제 환경에 맞는 프로젝트 설정·미리보기 지침을 적용한다.
4. 이번 요청은 로컬 검수이므로 새 사이트 등록·버전 배포·접근 권한 변경은 하지 않는다. 이미 연결된 프로젝트라면 그 식별 정보를 보존한다.

### 이번 프로젝트에 적용할 우선 조건

Sites의 일반적인 제작 기본값보다 이 문서에 기록된 사용자 조건을 우선한다.

- 일반 반응형 기본값을 이유로 모바일 화면을 추가하지 않는다.
- 이미지 제작을 먼저 시작하는 흐름을 적용하지 않는다. 이미지 생성·검색·첨부 이미지 삽입·영상 제작을 하지 않는다.
- 빠른 전체 제작 흐름을 이유로 대표 UI 검수 단계를 건너뛰지 않는다.
- 설치된 기본 UI 컴포넌트는 동작 기반으로 활용할 수 있다. 외형은 이번 콘셉트에 맞게 설계한다.
- 수정 후 배포라는 기본 흐름 대신 이번 요청의 로컬 검수 조건을 따른다. 후속 배포 요청에는 당시의 사이트와 공개 범위를 확인해 적용한다.
- 사용자가 별도로 요청하지 않은 외부 앱 연결, 실제 인증, 데이터베이스, 실거래 기능을 추가하지 않는다.

### 미리보기와 전달

브라우저 검수는 해당 환경이 지원하는 Sites 미리보기와 브라우저 도구로 실행한다. 미리보기가 불가능하면 원인을 보고하고, 코드 확인과 실제 화면 확인을 구분한다. 지원되지 않는 미리보기 주소를 임의로 추측하지 않는다.

현재 확인된 managed-linux 환경에서는 로컬 미리보기가 에이전트 검수용이다. 사용자에게 직접 접속할 수 없는 주소를 전달하지 않고 화면 캡처와 동작 확인 결과를 제출한다. 다른 환경에서 사용자용 로컬 미리보기가 제공되면 그 방식을 활용한다.

사용자가 직접 조작할 Sites 링크를 후속으로 요청하면, 해당 검수 범위를 완성한 별도 스포츠 데모에 배포한다. Sites 배포 URL을 임시 로컬 미리보기라고 설명하지 않는다.

## 4. 디자인 기준과 실제 크기

### 참고 자료의 역할

| 자료 | 참고할 부분 |
| --- | --- |
| [COBALT](https://titan-solution-t03.pages.dev/) | 고정 3열과 스포츠 카드의 구성. 중앙 히어로·바로가기는 이번 범위에서 제외 |
| [CAT VILLAGE](https://titan-solution-t01.pages.dev/) 등 사용자가 제시한 완성 데모 4종 | 헤더부터 카드·버튼까지 일관되게 마감된 완성도 |
| 사용자 제공 WOG 운영 사이트 스크린샷 | 스포츠 UI의 최소 품질 기준. 제목판·프레임·카드·버튼의 세부 마감 |
| [HADES](https://hades-arcade-v0-1.kexxadrix.chatgpt.site/) | 사용자 디자인을 동적인 웹 경험으로 구현한 Sites 사례 |
| 첨부 카지노 이미지 5개 | 이후 배너의 분위기 참고. 이번 화면에는 사용하지 않음 |

참고 자료가 전달되지 않았거나 열리지 않으면 실제로 확인한 것처럼 보고하지 않는다. 접근 가능한 자료와 고정 조건으로 진행하고, 빠진 품질 참고 자료를 검수 보고에 명시한다. 다른 사이트의 브랜드나 이미지를 복제하지 않는다.

### 비주얼 방향

**따뜻한 블랙 표면, 여러 명도의 골드 프레임, 아이보리 정보층**으로 설계한다. 빽빽한 스포츠 정보를 읽기 쉽게 정렬하면서 패널·버튼·타이틀의 재질과 단차를 충분히 표현한다.

아래는 검수할 초기 제안값이며 사용자 확정 색상 코드는 아니다.

| 역할 | 초기 값 |
| --- | --- |
| 바탕 | `#0C0B09` |
| 패널·단차 | `#181610`, `#211D15` |
| 골드 음영·기본·광택 | `#735427`, `#C8A45C`, `#F0D99E` |
| 주요 문자·보조 문자 | `#F3EBDD`, `#B7AA94` |

단색 노란 테두리만으로 금속을 표현하지 않는다. 그라데이션·안쪽 경계·밝은 윗면·그림자·CSS 패턴을 함께 다듬는다. 헤더, 섹션 프레임, 내부 패널, 누르는 버튼의 깊이와 역할을 구분한다.

로고는 첫 사이클에서 타이포그래피와 CSS 장식으로 구성한다. 일반 문자와 데이터는 HTML로 유지한다. 한국어 폰트·굵기·자간·줄 높이를 함께 검토하고, 점수와 배당률은 숫자가 바뀌어도 정렬이 유지되게 한다.

이미지 없는 홍보 패널도 짧은 문구·타이포그래피·프레임·동작 버튼으로 완결한다. 빈 상자나 ‘이미지 예정’ 표시로 남기지 않는다. 인물이나 카지노 장면을 CSS로 그리려는 작업은 하지 않는다.

### 크기와 스크롤

- 1920×1080은 모니터 해상도다. 브라우저 탭·주소·즐겨찾기 표시줄을 제외한 실제 콘텐츠 높이를 사용한다. 1080px 높이를 그대로 콘텐츠 높이로 고정하지 않는다.
- F11 전체화면 사용을 요구하지 않는다. 검수 환경의 모니터 해상도, 확인 가능한 브라우저 확대율, 실제 `innerWidth`·`innerHeight`를 기록한다. 확인할 수 없는 값은 추정하지 않는다.
- 초기 배치 제안: 왼쪽 272px, 오른쪽 320px, 외곽 여백 12px씩, 열 간격 12px씩. 콘텐츠 너비가 1920px일 때 중앙 너비는 `1920 − (12×2) − 272 − 320 − (12×2) = 1280px`이다.
- 헤더 높이는 약 68px에서 검토한다. 공지 띠를 사용하면 그 높이를 따로 포함한다. 이 치수는 초기 제안이며 실제 글자와 카드 밀도로 조정한다.
- 실제 크기 와이어프레임으로 배치를 짧게 확인한 뒤 같은 코드에서 대표 UI로 발전시킨다. 별도 와이어프레임 문서나 장기간의 설계 단계를 만들지 않는다.
- 중앙 목록은 세 분류를 한 화면에 억지로 축소하지 않고 스크롤한다. 각 영역의 끝에서 다른 영역으로 스크롤이 의도치 않게 전달되는지 확인한다.
- 오른쪽 계정 패널이 슬립을 과도하게 밀어내지 않게 한다. 선택 목록이 길어져도 금액·합계·실행 버튼에 쉽게 접근할 수 있게 구성한다.

## 5. 첫 제출 — 대표 UI와 수정 통제 검증

먼저 실제 페이지의 위치와 크기로 다음 대표 요소를 함께 구현한다. 독립된 장식 샘플이나 컴포넌트 목록만 제출하지 않는다.

- 헤더와 실시간 스포츠 선택 상태.
- 실시간 스포츠의 제목판·LIVE 배지·건수 표시.
- 리그·경기 상태·팀명·스코어·배당을 갖춘 베팅카드 1개.
- 왼쪽 바로가기 패널과 이미지 없는 홍보 패널.
- 오른쪽 계정 패널과 빈 상태·선택 상태의 베팅슬립.
- 배당 버튼의 기본·호버·눌림·선택·사용불가 상태.

첫 제출부터 **배당 선택 → 슬립 반영 → 선택 제거**가 로컬 상태로 작동해야 한다. 나머지 검색·계정 전환·금액 조작은 전체 페이지 확장 단계에서 완성한다. 대표 UI의 강한 호버·광택·대기 효과도 함께 시험한다.

### 베팅카드 설계

경기 정보, 팀과 스코어, 마켓과 선택 버튼의 읽는 순서를 명확하게 만든다. 승패·오버/언더·핸디캡의 기준점과 선택 대상이 구분되어야 한다. 리그·진행 상태·마켓이 서로 맞는 가상 데이터를 사용하고 경기 수와 마켓 수를 혼용하지 않는다.

긴 팀명, 소수 배당률, 잠금 상태에서도 같은 정렬을 유지한다. 선택 상태는 호버와 명확하게 달라야 한다. 배당 상승·하락은 화살표 등으로 구별하고, 보조 신호색이 필요하면 별도 제안으로 검수한다.

### 수정 범위를 통제하는 구조

규모에 맞게 다음 책임을 분리한다. 파일 개수나 새로운 라이브러리 도입을 목표로 삼지 않는다.

| 책임 | 관리할 내용 |
| --- | --- |
| 공통 스타일 | 색상, 열 너비, 간격, 글자, 프레임 규칙 |
| 컴포넌트 | 헤더, 섹션 제목, 베팅카드, 배당 버튼, 사이드 패널, 슬립 |
| 모션 | 호버 시간, 광택 강도, 대기 효과 강도·주기 |
| 데모 상태 | 고정 가상 경기, 선택 항목, 금액, 계정 표시 상태 |

조절값은 소스에서 관리한다. 방문자 화면에 개발용 슬라이더나 제어 패널을 추가하지 않는다. 전후 비교 중에는 동일 데이터·선택 상태·스크롤 위치를 사용한다.

### 반드시 실행할 통제 테스트

| 테스트 | 바꿀 항목 | 유지해야 할 항목 |
| --- | --- | --- |
| A | 대표 카드의 호버 광택 강도 | 카드 크기·위치, 글자, 선택 상태, 슬립 |
| B | 섹션 제목판의 경계·장식 | 헤더, 베팅카드, 슬립 |
| C | 대표 대기 애니메이션 끄기·켜기 | 버튼 클릭, 선택 표시, 배당 선택 동작 |

테스트마다 한정된 수정으로 적용하고 전후 화면 또는 관찰 결과를 남긴다. 시각적 변화는 실제 브라우저에서 확인한다. 코드가 바뀌었다는 이유만으로 통과시키지 않는다. 테스트용 변경을 정리하고 최초 기준 또는 의도한 검수 상태로 복원한다.

### 첫 검수 제출물과 종료 지점

1. 실제 크기 페이지 화면과 카드·슬립 상태 화면.
2. 배당 선택·제거 및 독립 스크롤 확인 결과.
3. 통제 테스트 A~C의 통과·실패·미확인 결과와 근거.
4. 수정한 부분, 사용자 판단이 필요한 디자인 항목, 다음 작업을 합쳐 짧게 보고.

문서만 제출하거나 ‘완료’라는 설명만 남기지 않는다. 검수 해상도가 목표 환경과 다르면 그 차이를 표시한다. **이 결과물을 제출하고 사용자 검수를 기다린다.** 사용자에게 이미 확정받은 색상 조합·기기 범위·페이지 수를 다시 묻지 않는다.

## 6. 대표 UI 승인 후 — 전체 페이지 완성

검수 수정사항을 반영한 공통 규칙으로 실시간 스포츠·마감임박·인기경기와 좌우 전체 콘텐츠를 확장한다. 세 분류는 공통 프레임을 공유하되 제목판의 상태·배지·강조에 차이를 준다.

| 영역 | 완성할 데모 동작 |
| --- | --- |
| 경기 목록 | 가상 경기 검색·종목 필터, 결과 없음 |
| 배당 | 선택·해제·잠금, 상승·하락 표시 |
| 슬립 | 빈 상태·1개·여러 개, 개별 제거·전체 제거 |
| 금액 | 입력·빠른 추가·초기화, 합계와 예상 금액 갱신, 잘못된 입력 처리 |
| 계정 | 실제 인증정보 없이 가상 로그인 전후·로그아웃 상태 전환 |
| 기타 메뉴 | 충전·환전·내역·문의의 데모 패널 또는 안내 |
| 최종 동작 | 가상 선택 내용의 확인 피드백. 실제 거래 성공으로 표시하지 않음 |

강한 버튼 글로우, 광택 이동, LIVE 맥동, 프레임 조명, 배당 변동 효과를 적용할 수 있다. 효과 때문에 카드가 밀리거나 수치가 흔들리면 수정한다. 조작과 정보 읽기를 유지하면서 검수로 강도를 조정한다.

사용자에게 전체 화면을 제출하고 수정사항을 반영한다. 반응형 작업이나 다른 카테고리의 페이지로 범위를 확장하지 않는다.

## 7. 통과 기준과 인계

- 이미지 없이 헤더·제목판·카드·슬립·홍보 패널이 같은 디자인 규칙으로 완결된다.
- 실제 브라우저 콘텐츠 영역을 기준으로 고정 3열과 독립 스크롤이 유지된다.
- 버튼의 호버·선택·사용불가가 구분되고, 긴 팀명·여러 슬립 항목에서도 구조가 유지된다.
- 첫 제출은 대표 UI와 테스트 A~C, 전체 완성 제출은 6절의 동작까지 확인한다.
- 실제 렌더링 검증, 코드 확인, 미확인 항목을 구분해 보고한다.
- 시각적 품질 통과는 사용자 검수로 결정한다. WOG 운영 화면을 최소 품질 참고로 사용한다.
- 승인된 상태와 후속 변경을 구분할 수 있게 소스 이력을 남긴다. 지시서를 여러 중복 문서로 늘리지 않는다.

완료 보고는 화면을 먼저 제시하고, 구현 범위·검증 결과·남은 항목을 짧게 적는다. 후속 담당자가 이어갈 수 있도록 프로젝트 위치와 실행 방법을 함께 남긴다. Sites 기능이 없는 환경으로 인계할 때는 그 한계를 명시하고, 기존 소스의 실행·수정 가능 범위를 확인한다.

## 8. 후속 이미지·영상 사이클

현재 첫 사이클과 분리한다. 확정된 배너·패널 슬롯에 한해 표시 크기, 비율, 인물 위치, 문자 여백, 크롭 안전영역, 파일 형식을 정리하면 사용자가 필요한 이미지를 제작해 전달한다. 약 6초 WebM도 이 단계에서 필요성을 판단한다.

슬롯은 현재 CSS 패널의 구조를 유지하며 매체를 추가할 수 있게 구성한다. 가로·세로 참고 이미지가 있다는 이유로 배너 비율을 강제하지 않는다. 현재 문서는 이미지나 영상 생성 요청이 아니다.
